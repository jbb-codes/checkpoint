# OS-native socket activation on macOS/Linux, lazy CLI-triggered spawn on Windows

The daemon must start automatically on first use and not sit idle consuming resources, and must survive a crash without losing in-flight run state. On macOS (launchd) and Linux (systemd) we use OS-level socket activation: the OS starts the daemon on first connection, stops it when idle, and restarts it on crash, with in-flight state resumed from SQLite. Windows has no equivalent primitive in this scope, so the CLI instead checks daemon reachability and spawns it detached on every invocation if unreachable. This means the two platforms genuinely behave differently (Windows has no idle-shutdown or crash-restart guarantee) — accepted because Windows Service Triggers, which would close that gap, were out of scope for this round. The daemon's socket-acquisition logic does depend on which mechanism started it: systemd hands over a bound-but-not-listening socket, which the daemon listens on directly; launchd hands over one that is already listening, and re-listening on it crashes with ENOTTY on macOS, so the daemon closes that fd and self-binds a fresh socket at the same path instead (see `src/daemon/activation.ts`).
